Part 1The conceptWhat PostgreSQL is and the ideas you need before reading the code.

Collapsed

PostgreSQL is the relational database that stores Shopfront's products and orders. The API talks to it through node-postgres (the pg package): the low-level Node.js driver that keeps a pool of connections, sends your SQL with its values, and turns result rows into JavaScript objects. Sources: node-postgres, PostgreSQL versioning, server/db.js.

In one paragraph

  • PostgreSQL stores data in tables you query with SQL. It runs as its own server; the API connects to it over the network.
  • node-postgres keeps a pool of open connections, so each query doesn't pay for a new one (Pool).
  • You write the SQL yourself. Values go in separately as $1, $2… (Queries).

The problem it solves

  • Durable, consistent storage: rows survive restarts, and many API requests can read and write at once.
  • node-postgres handles the connection protocol, pooling, and type conversion (json columns become objects, timestamps become Dates).

Compared with

  • Query builders and ORMs such as Knex sit on top of pg and write the SQL for you (Knex). Shopfront uses the driver directly: four hand-written queries.

How Shopfront uses it

  • One shared pool from DATABASE_URL, two tables, four queries, all parameterized (usage map).
  • No schema, migrations, or seeds in the repo, and no tests that touch the database.

Follow one write, placing an order with POST /api/orders, from the handler to PostgreSQL and back. The Express walkthrough covers the same request up to the handler; this one picks up there. Sources: server/routes/orders.js, server/db.js.

createOrder passes two things: SQL with a $1 placeholder, and an array of values. The cart is turned into a JSON string first. Concept: parameterized queries.

db is the shared pool from server/db.js. pool.query borrows a connection, runs one statement on it, and gives the connection back. Concept: pool.

The SQL text and the values travel separately, so the cart's contents can't change the meaning of the SQL. PostgreSQL treats $1 as data, whatever it contains.

PostgreSQL inserts a row into orders and, because of returning id, sends back the id it generated, in the same round trip. Where the flow stops today: the repo doesn't define the orders table, so the column types (is items json, jsonb, or text?) can only be read from a running database.

db.query resolves to a result object; Shopfront uses only rows, an array of plain objects keyed by column name. rows[0].id is the new order's id. If the query fails, the promise rejects, and because the handler has no try/catch, that crashes the process in Express 4 (see the Express gotchas).

Shopfront's database code gets the most important thing right: every value is parameterized. The gotchas are about what happens when something goes wrong. Sources: server/db.js, server/routes/.

Conventions here

  • One shared pool, required as db from server/db.js, the single module the node-postgres project-structure guide recommends.
  • Always parameterized: $1 with a values array in all 4 queries, never string concatenation.
  • JSON is stringified on purpose: JSON.stringify(req.body.items) (server/routes/orders.js:6). Passing the array itself would send a Postgres array, not JSON.
  • Ids come back with RETURNING instead of a second query.

Gotchas

  • No pool error listener. If the database drops an idle connection, node-postgres emits an error on the pool; with no pool.on('error') in server/db.js, that can crash the process (Pool).
  • Query errors crash the server too: handlers await db.query with no try/catch, and Express 4 doesn't catch rejected promises (Express gotchas).
  • A missing DATABASE_URL fails quietly. In current node-postgres releases, an undefined connection string falls back to PG* variables and localhost, so a misconfigured server starts fine and only fails on its first query.
  • No schema in the repo. Column types, constraints, and indexes exist only in whatever database you point at. If id is a bigint, it comes back as a string ("42", not 42).
  • No connection timeout. The pool's default is to wait forever for a free connection, so a leak or a stuck database makes requests hang rather than fail.

Shopfront allows any pg 8.x from 8.11.0; with no lockfile, a fresh install gets the newest 8.x. The repo doesn't say which PostgreSQL server version it targets. Checked 2026-10-13. Sources: package.json:10 (no lockfile committed).
